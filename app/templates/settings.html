    Local {{ app_name }} server mode

    How multiple local instances (below) get combined behind one URL — only matters once instance count is more than 1. Local (default) makes this app balance the load itself: this instance forwards each request to whichever local instance is least busy and streams the reply straight back — no external proxy needed. External balancing leaves it to your own external reverse proxy instead.

    Local instances

    How many local {{ app_name }} processes should be running on this machine, sharing the same database/models/knowledge base — takes effect immediately, no restart needed. A single instance (the default) is a plain-text answer to "no scaling"; anything above that only does something once combined behind one URL — either your own external reverse proxy (nginx/Caddy), or the built-in "Local {{ app_name }} server mode" option above. See ROADMAP.md's "Concurrency" section.

      Database

      Which database {{ app_name }} stores everything in. Saving builds the schema if needed and switches {{ app_name }} over immediately — no restart needed.

      Switching does not move anything from the current database. The new database only ever gets the same starter data a fresh install gets (one admin account, 3 default notes) — every existing conversation, message, channel, non-admin user, and document, plus every admin setting on this page and elsewhere (RAG limits, model visibility, channel delivery mode, and so on), stays behind in the old database and won't be visible here anymore. Nothing is deleted, but nothing is copied over either.
      The .env file was edited by hand and doesn't match what's currently running — save here (or restart) to bring them back in sync.

      Create the database and user yourself first, with utf8mb4_bin collation — see "Switching to MySQL" in README.md. This only connects to an existing database, it won't create one for you.

      Chat titles

      How a brand-new chat's sidebar title is picked, for every user. "Simple" builds it instantly from the first message itself, with no model call. "Smart" asks the model to invent one instead — can read more naturally, at the cost of a second, slower generation call after the reply.

      Channel replies

      How other members of a channel find out about a reply while they're sitting in that chat. Either way, a reply now finishes and saves even if whoever sent it navigates away mid-stream — this only affects who else finds out about it, and how. "Cheap" has other members' tabs check back every few seconds — no extra server load beyond that. "Real" pushes it to them live, token-by-token, but only reliably reaches everyone when running as a single app instance (Admin settings > System > instance count). The second setting is whether the model also reads the messages members post to the channel without asking it, when it answers a later question: "Skip" keeps its prompt shorter and faster.

      Reply timeout

      How long the app waits for a model to finish generating a text-only reply — personal chat or channel alike — before giving up and marking it failed. A backstop against a hung or pathologically slow request tying up resources indefinitely. Set to 0 for no timeout, if this server's hardware genuinely needs longer than any reasonable limit for one reply. A reply with an image attached uses the separate, more generous timeout below instead.

      Vision reply timeout

      Same as Reply timeout above, but for a message with an image attached. Encoding an image (before any reply text even starts streaming) is dramatically slower than plain text on CPU-only hardware — confirmed to take several minutes on its own for a single modest photo — so this needs real headroom of its own rather than sharing the text timeout above. Set to 0 for no timeout.

      Data retention

      How long the Stats page's Telemetry and System views keep their history before it's swept away — see those pages for what each actually tracks. Kept small by default so neither table grows unbounded over a long uptime; raise either if you want a longer look-back window.

      Which engine below actually answers chat and embedding requests. Ollama and Matricxon can each be configured and started independently of this choice — switching here doesn't stop or start either one, it only changes where new requests go.
